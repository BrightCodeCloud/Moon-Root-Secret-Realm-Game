## 1. 结论

**可行性：高。**

《月根秘境》可以使用 C# 开发为真正的 Windows 桌面游戏，并输出可离线运行、可通过安装向导安装和卸载的应用程序。它不需要浏览器，也不需要在玩家电脑上预装 Visual Studio。

推荐技术路线：

> **Godot 4.7.1 .NET + C# + Visual Studio 2022 + Windows x64 导出 + Inno Setup 安装包**

这一组合最适合当前项目的原因：

- 游戏是纯 2D 像素风，Godot 有专用 2D 渲染、物理、TileMapLayer、动画和粒子系统。
- C# 可用于全部核心玩法、敌人 AI、随机房间、存档和数据系统。
- Godot 支持把 .NET 项目导出到 Windows、Linux 和 macOS 桌面平台。
- 像素画可使用低分辨率视口与整数倍缩放，避免像素粗细不均。
- 引擎采用 MIT 许可，可用于商业游戏；只需在发布物中保留相应许可声明。
- 相比自行搭建图形框架，房间编辑、碰撞、动画、UI 与资源导入的开发量更低。

Godot 官方资料：

## 2. “可安装应用程序”的最终形态

推荐提供两个发布包：

1. **安装版**：`MoonrootSetup-x64.exe`
   - 安装到用户选择的目录。
   - 创建开始菜单和桌面快捷方式。
   - 提供卸载程序。
   - 可选自动启动、文件校验和静默安装参数。
2. **免安装版**：`Moonroot-Windows-x64.zip`
   - 解压后直接运行。
   - 便于内测、媒体评测和故障排查。

Godot 负责生成游戏可执行文件与资源包；Inno Setup 将导出目录封装成单个安装程序。Inno Setup 官方说明其可生成单一 EXE 安装包，并支持 64 位 Windows 和卸载功能：[Inno Setup 介绍](https://jrsoftware.org/ishelp/topic_whatisinnosetup.htm)。

### 2.1 玩家侧依赖

目标是采用完整导出，让玩家安装后直接运行，不要求额外安装：

- .NET SDK
- Visual Studio
- Godot 编辑器
- 浏览器或本地服务器

正式发布前应在一台没有开发环境的干净 Windows 虚拟机上验证安装、运行、存档、升级与卸载。

### 2.2 安装包与存档分离

- 程序和只读资源安装在应用目录。
- 存档、设置、日志写入用户数据目录。
- 卸载程序默认保留存档，并提供明确的“同时删除存档”选项。
- 安装新版本不覆盖用户存档。
- 存档使用版本号和迁移逻辑，避免更新后损坏旧进度。

## 4. 引擎方案对比

| 方案 | 2D 像素适配 | C# 体验 | 编辑器与内容制作 | Windows 发布 | 项目代价 | 结论 |
|---|---|---|---|---|---|---|
| **Godot .NET** | 优秀 | 良好 | 完整且轻量 | 原生支持 | 低至中 | **首选** |
| Unity | 优秀 | 优秀 | 生态最丰富 | 原生支持 | 中至高 | 团队扩大时的备选 |
| MonoGame | 良好 | 原生 C# | 需要自建大量工具 | 支持 | 高 | 适合偏底层的程序团队 |

### 4.1 Godot .NET

优势：

- 专门的 2D 渲染与物理系统，而不是在 3D 空间中模拟 2D。
- TileMapLayer 可承载地面、遮挡、碰撞和导航相关数据，适合随机房间骨架。
- Scene/Node 结构适合把角色、敌人、投射物、植物和房间做成可复用单元。
- 输入映射同时支持键盘、鼠标和手柄；官方文档提供 C# 示例。
- 内置视口缩放可使用整数倍率显示像素画。
- 引擎和编辑器体积、启动速度、版本控制负担相对较小。
- 无订阅费和运行时抽成，商业发布边界清晰。

限制：

- C# 热重载时通常不能完整保留场景运行状态。
- 一部分社区教程优先使用 GDScript，需要把概念转换为 C#。
- 主机平台不是当前原型目标；未来移植通常需要认证第三方服务商。
- 必须下载明确标注 **.NET / C# support** 的 Godot 版本；数字商店版本可能不包含 C# 支持。

Godot 当前官方下载页提供独立的 .NET 版本和 .NET 导出模板，并要求本机安装 .NET SDK：[Godot Windows 下载页](https://godotengine.org/download/windows/)。

### 4.2 Unity

优势：成熟的 C# 工作流、Profiler、2D 工具和大型资源生态；如果未来目标包括多人协作、商业中间件或更复杂的跨平台发布，Unity 的人才与插件储备更丰富。

代价：编辑器和工程更重，项目配置与包管理复杂度更高；对当前规模的 2D 像素 Roguelike 有一定过度配置。授权条款也需要随商业规模持续复核。Unity 官方 2026 年说明中，Personal 方案适用于年收入与资金不超过 20 万美元的用户，超过后需要 Pro：[Unity 方案与定价更新](https://unity.com/products/pricing-updates)。

选择 Unity 的条件：团队成员已有成熟 Unity 经验，或明确依赖 Unity 专属插件、主机渠道和招聘市场。

### 4.3 MonoGame

MonoGame 是 C# 游戏框架，不是带完整场景编辑器的引擎。它能提供窗口、图形、音频、输入和内容管线，但随机房间编辑器、碰撞可视化、动画状态机、UI 布局等需要自行开发或组合第三方工具。

优势是代码控制力强、运行层简单、跨桌面平台方便。官方支持 Windows、macOS、Linux 以及移动端；但其官方介绍也明确强调“自带工具”的框架定位：[MonoGame 平台支持](https://docs.monogame.net/articles/getting_started/platforms.html)、[MonoGame 项目介绍](https://monogame.net/presskit/)。

对本项目而言，MonoGame 会把大量时间消耗在制作工具而非验证“种植战斗”核心，因此不作为首选。

## 5. 推荐工具链

### 5.1 必需工具

| 环节 | 推荐工具 | 使用方式 |
|---|---|---|
| 游戏引擎 | Godot 4.7.1 .NET stable | 场景、2D 渲染、物理、输入、UI、导出 |
| 编程语言 | C# | 全部运行时代码 |
| 目标框架 | `net8.0` | 优先稳定兼容，不追逐最新语言运行时 |
| IDE | Visual Studio 2022 Professional | 编码、调试、测试与性能分析 |
| 版本控制 | Git | 源码、场景和配置版本管理 |
| 安装包 | Inno Setup | 生成 Windows 安装与卸载程序 |

建议用 `global.json` 固定团队 SDK，避免不同开发机自动选中 .NET 10 后产生不一致；具体版本在创建技术原型时再确定，不在当前设计阶段新增配置文件。

### 5.2 美术与音频工具

- 像素美术：Aseprite 优先；免费路线可选择 LibreSprite 或 Krita。
- 大型概念图和宣传图：Krita、Photoshop 或生成式图像作为方向稿，正式游戏资产必须回到统一像素网格。
- 音效：Audacity 负责裁切、降噪和响度处理；合成音效可另选专用工具。
- 音乐：由作曲软件导出 OGG；循环点和响度规范在音频制作前制定。

这些工具不是当前立即安装项，先确认引擎原型方向后再决定授权和工作流。

## 6. 推荐技术结构

建议采用“Godot 场景负责表现与组合，纯 C# 类负责规则与数据”的分层方式。

| 层 | 职责 | 示例 |
|---|---|---|
| Core | 不依赖具体场景的游戏规则 | 伤害计算、随机种子、掉落权重 |
| Gameplay | 运行时实体行为 | 玩家、敌人、投射物、植物、地块 |
| Rooms | 房间生成与进度 | 房间骨架、敌人预算、出口、波次 |
| Data | 可编辑内容定义 | 武器、种子、遗物、敌人数值 |
| Presentation | 画面、动画、音效、震动 | Sprite、粒子、音频事件、镜头 |
| UI | 菜单和 HUD | 主菜单、构筑卡片、地图、结算 |
| Platform | 平台服务 | 存档路径、窗口、成就、日志 |

### 6.1 数据驱动原则

- 敌人、遗物、种子和房间奖励使用 Godot Resource 或等价数据资产。
- 代码定义行为类型，数据定义数值和可组合参数。
- 随机生成使用可记录的整数种子，方便复现 Bug。
- 核心伤害与掉落计算尽量与渲染节点解耦，便于自动化测试。
- 不在场景脚本中硬编码大量物品表或敌人组合。

### 6.2 像素显示设置

根据现有美术规范，技术原型建议采用：

- 设计视口：`640 × 360`。
- 比例：16:9。
- 拉伸模式：Viewport。
- 缩放模式：Integer。
- 纹理过滤：Nearest。
- 默认窗口：`1280 × 720`，允许无边框窗口和独占全屏。

Godot 官方也将 640×360 列为桌面像素游戏的良好基准，可整数缩放至 720p、1080p、1440p 和 4K。

## 7. 开发与发布阶段

### 阶段 A：技术探针，预计 3–5 个工作日

不制作完整游戏，只验证：

- C# 项目能编译、调试和导出。
- 像素画在常见分辨率下无拉伸失真。
- 键鼠与手柄输入正常。
- 200–500 个投射物和基础碰撞的性能余量。
- 存档可写入用户目录。
- 导出包能在无开发环境电脑上运行。

### 阶段 B：核心玩法原型，预计 6–10 周

- 单角色、单房间循环。
- 移动、瞄准、射击、翻滚。
- 三种种子、三种土地状态。
- 六种敌人和一个 Boss。
- 占位 UI、存档、暂停和结算。

目标是验证“种植是否真的让战斗更有趣”，不追求正式美术量。

### 阶段 C：垂直切片，预计 3–5 个月

- 一个完整区域达到接近发行质量。
- 正式角色、敌人、环境、音效和 UI。
- 随机房间、局内构筑、营地最小闭环。
- 安装包、崩溃日志、设置和基础兼容测试。

以上为一名熟悉 C#、初次或较少使用 Godot 的全职开发者估算；兼职开发或同时承担全部美术与音频时，周期可能扩大至两到三倍。

## 8. 主要技术风险

| 风险 | 等级 | 应对 |
|---|---|---|
| 同屏弹幕、敌人和植物节点过多 | 中 | 对象池、分组碰撞、限制粒子、性能预算测试 |
| 随机房间出现不可通行或不公平组合 | 中 | 人工房间骨架 + 自动可达性检查 + 固定随机种子复现 |
| C# 与场景节点耦合过重 | 中 | 规则数据与表现分层，禁止大型“万能管理器” |
| 像素图在非整数分辨率下变形 | 低 | 固定设计视口、整数缩放、分辨率矩阵测试 |
| 存档随版本更新损坏 | 中 | 存档版本、迁移、备份和原子写入 |
| 未签名安装包触发 Windows 警告 | 中 | 内测接受提示；公开发行前评估代码签名证书 |
| Godot C# 热重载体验有限 | 低 | 缩短测试场景，使用小型可复现房间与自动测试 |
| 未来主机移植 | 中至高 | 首版只承诺 Windows；主机需求出现后单独立项 |

## 9. 不推荐的路线

### 9.1 WPF / WinForms

它们适合桌面工具和业务界面，不适合高频绘制、精灵动画、物理碰撞和大量游戏实体。即使能做，也需要额外搭建渲染与内容系统，投入不合理。

### 9.2 纯 .NET 控制台或网页套壳

不能满足图形游戏需求，或违背“不是网页版”的产品目标。

### 9.3 首版同时支持所有平台

会显著增加输入、分辨率、存档、签名和发行测试成本。推荐先做好 Windows x64；游戏规则保持平台无关，为后续移植留接口。

## 10. 安装前决策清单

进入开发前只需确认以下事项：

1. 同意以 **Godot .NET + C#** 作为首选技术路线。
2. 首发平台确定为 **Windows 10/11 x64**。
3. 原型目标采用 640×360 设计视口和 16×16 地块。
4. 首个里程碑只验证单房间战斗与种植连锁。
5. 确认是否购买 Aseprite，或先使用免费美术工具。
6. 明确安装包首期采用 Inno Setup，商店发布暂不处理。

以上路线已经确认，最小技术探针、可玩原型、Windows 导出与安装包均已完成。后续按原型验收结果继续拆分代码、补充正式内容并做干净环境兼容测试。

## 11. 最终建议

采用 Godot .NET。它对本项目不是“勉强可用”，而是与 2D 像素、房间编辑、C#、Windows 桌面发布和小团队成本高度匹配。

本机已经具备 Visual Studio 2022、.NET 8 和 Git，Godot 4.7.1 .NET 也已作为项目本地工具完成验证。技术探针已经确认程序集编译、主场景装载、中文界面、像素整数缩放、Windows x64 导出和双语安装程序均可行；下一步是继续迭代垂直切片并在干净的 Windows 环境中补充安装、运行与卸载测试。
